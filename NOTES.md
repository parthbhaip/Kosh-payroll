## T06 Users and roles (2026-10-06)
- Built: `V1__create_users.sql` (first migration: `users` with `uk_users_email`, `ck_users_email_lower`, `ck_users_failed_login_count`; `user_roles` (PK `user_id, role` doubles as the FK index, `fk_user_roles_user`, `ck_user_roles_role` listing the six roles, `idx_user_roles_role` for T08's role filter)), `com.kosh.user.User` (entity on `BaseEntity`; roles as an `@ElementCollection` `Set<Role>`), `UserRepository`.
- Decisions: e-mails are stored `strip().toLowerCase(Locale.ROOT)` (`User.normalizeEmail`), so the unique key is case-insensitive on H2 too and lookups hit it directly. Use `findByEmailIgnoreCase`/`existsByEmailIgnoreCase` (default methods that normalise, blank or null finds nobody; the find fetches roles with an entity graph, one query) - T07's `UserDetailsService` and T08's invite and duplicate check must call these. The raw exact-match methods are named `findWithRolesByEmail`/`existsExactlyByEmail` so nobody picks them by name: with un-normalised input they miss on H2 (case-sensitive) but match on MySQL (ci collation). `ck_users_email_lower` only bites on H2: on MySQL the ci collation makes `email = LOWER(email)` always true, so `User.normalizeEmail` is the only guard there and any seed or native SQL must insert e-mails already lower-case (no vendor-only BINARY/COLLATE, to keep the SQL portable). A user needs at least one role: `setRoles` (and the constructor) reject an empty set, so T08's invite and edit-roles forms must require one. `password_hash` is nullable: null means invited, no password yet - T07 must reject sign-in for it, T08 sets it from the invite link. `VARCHAR(100)` fits a `{bcrypt}` delegating hash. Role column carries `@JdbcTypeCode(SqlTypes.VARCHAR)` because Hibernate's MySQL dialect expects a native ENUM for `@Enumerated(STRING)`; reuse that on every enum column.
- Sign-in state lives on the entity for T09: `recordLoginFailure()` (returns the new count), `lockUntil(t)`, `isLockedAt(now)` (lock ends exactly at `lockedUntil`), `recordLoginSuccess(at)` (clears count and lock, sets `lastLoginAt`). `setRoles` replaces the set in place; `getRoles()` is read-only. No employee link yet: T15 adds `users.employee_id` (nullable, FK + index) in its own migration together with the employees table.
- Tests: `UserTest` (unit) and `UserRepositoryTest` - `@DataJpaTest` + `@AutoConfigureTestDatabase(replace = NONE)` (package `org.springframework.boot.jdbc.test.autoconfigure`) so it runs the real Flyway schema on the test profile's MySQL-mode H2 with `ddl-auto=validate`; the default would swap in a plain embedded H2. It shares the `kosh` mem DB with the `@SpringBootTest` contexts (rolled back per test), so it uses `@repo.kosh.test` addresses that later tests will not commit.
- Gotcha: `@DataJpaTest` scans repositories from `KoshApplication`'s package, so a slice whose `@EntityScan` leaves out an entity fails with "Not a managed type". `BaseEntityJpaTest` (probe entity only) now sets `spring.data.jpa.repositories.enabled=false`; do the same in any future probe-style slice.

- Built in `com.kosh.security`: `KoshUserDetailsService` (by `findByEmailIgnoreCase`; an invited user with no password hash is "not found", so the form answers as for a wrong e-mail; `accountNonLocked` from `User.isLockedAt(now)`), `KoshUserDetails` (Spring `User` + display name; `KoshUserDetails.displayName(auth)` falls back to the user name for mock principals - the shell, user menu and initials now use it), `Landing` (ADMIN /admin, HR /hr, PAYROLL /payroll, FINANCE /finance, else /me), `LoginController` (GET `/login`, signed-in users go to their landing; GET `/home` redirects to the landing - the app logo and the public header's "Open Kosh" link there), `LoginFailureHandler`. `SecurityConfig`: form login with `email`/`password`, a saved request (link opened before signing in) beats the landing, POST `/logout` -> `/login?logout`, remember-me 14 days (`REMEMBER_ME_DAYS`; `TokenBasedRememberMeServices`, key = `HmacHasher.deriveSecret("kosh/remember-me-key/v1")` (HMAC of the data key under its own label, never a look-up hash, so no typed value stored as a look-up hash can leak it), so it needs no new env var and a password change or disabling the account kills old cookies), `PasswordEncoder` bean (delegating, `{bcrypt}$2a$10$...`). `com.kosh.web.HomeController` + `templates/home/index.html`: the five area homes (greeting from the clock, workspace summary, signed-in e-mail and roles, "Your workspaces" cards when the roles open more than one, help card). `templates/auth/login.html`, `static/js/password-toggle.js` (loaded from `fragments/head` on every page; any `<button data-password-toggle aria-controls="id" hidden>` gets show/hide, hidden without JS).
- Authentication manager is a bean built by hand (`DaoAuthenticationProvider` + `RememberMeAuthenticationProvider`, events to Boot's `DefaultAuthenticationEventPublisher`) and set on the chain with `http.authenticationManager(...)`. Why: Spring's default checks "disabled" before the password, which tells a guesser the account exists; ours checks the lock before the password and disabled/expired only after a correct one. Decision (lock message trade-off): a locked account answers "This account is locked..." to any password, fast and without bcrypt, while unknown e-mails never lock, so once T09 locks after 5 failures anyone willing to lock an account learns it exists (and can lock it on purpose - inherent to per-account lockout). Accepted: work e-mails are guessable anyway, PLAN T09 asks for friendly messages, and T10 audits the failures. Rejected: checking the lock after the password (it would answer "locked" only to the right password, turning the lock into an oracle that confirms a correct guess). If T09 wants no enumeration, make `LoginFailureHandler.message` return `BAD_CREDENTIALS` for `LockedException` (one line; update `LoginTest.lockedUserIsRejectedEvenWithTheRightPassword`).
